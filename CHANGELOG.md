# Changelog

All notable changes to this project are listed here.
Versions follow [Semantic Versioning](https://semver.org/).

## [0.5.1] - 2026-10-25

### Fixed

- Requests that failed with an unhandled exception, such as the database
  being down, were answered with a 500 but never counted in
  `http_requests_total`. The availability SLO and its alerts were blind to
  that whole class of outage. Found during a manual game day: the database
  went down and no alert fired.

## [0.5.0] - 2026-10-25

Alerting: problems now reach a phone, with instructions attached.

### Added

- Alertmanager routing alerts to Telegram. Pages notify right away and repeat
  every hour; tickets arrive silently.
- Inhibition rules: a down service mutes its SLO alerts, and a page mutes
  the ticket for the same SLO.
- `OrdersApiDown` alert on `up == 0`, for the case where the app sends no
  data and the SLO alerts stay silent.
- Runbooks for every alert, linked from the alert itself.
- Unit tests for the alerting rules with `promtool test rules`.
- `scripts/e2e-alert.sh`, run in CI: stops the API and checks that
  `OrdersApiDown` reaches Alertmanager, reporting the time to detect.
- `scripts/generate-slo-rules.sh` to regenerate the Sloth rules.
- CI checks the Alertmanager config with `amtool`.

## [0.4.0] - 2026-10-25

SLOs: a clear line between "fine" and "not fine".

### Added

- Two SLOs as code in `slos/orders-api.yml`: 99.9% availability and 99% of
  successful requests under 250 ms, both over 30 days.
- Prometheus recording and alerting rules generated by Sloth, with
  multi-window, multi-burn-rate page and ticket alerts.
- "SLOs and error budget" dashboard: budget left, achieved vs objective,
  burn rate and firing alerts.
- Error budget policy in `docs/error-budget-policy.md`.
- CI validates the SLO specs, fails if the generated rules are stale and
  checks them with `promtool`.

## [0.3.0] - 2026-10-25

Logs and traces: from "errors went up" to the exact request that failed.

### Added

- OpenTelemetry zero-code instrumentation for FastAPI, psycopg and logging,
  configured only through `OTEL_*` environment variables.
- OpenTelemetry Collector routing traces to Tempo, logs to Loki and metrics
  to Prometheus over OTLP.
- Tempo 3.1 and Loki 3.7, provisioned in Grafana with links between them:
  exemplar → trace, trace → logs and log → trace.
- JSON logs on stdout with `trace_id` and `span_id`. In Loki the ids are
  structured metadata, never labels.
- A latency panel with exemplars on the Golden signals dashboard.
- Documentation in `docs/`: architecture, running locally, endpoints and ports.
- `scripts/smoke-test.sh`, run in CI: checks every service and that one
  request's trace and log line actually reach Tempo and Loki.
- CI validates the Collector config.

### Changed

- Database access goes through a connection pool. A trace showed that opening
  a connection per request cost about 4 ms against 0.1 ms for the query; p95
  latency of `/products` dropped from about 10 ms to about 5 ms.

## [0.2.0] - 2026-10-25

Metrics: the app can now be watched.

### Added

- RED metrics in `orders-api` at `/metrics`: `http_requests_total` (counter)
  and `http_request_duration_seconds` (histogram), labelled by route template
  so cardinality stays bounded. Unknown paths share the `unmatched` label.
- Prometheus (v3.15.1) scraping the API every 15 seconds.
- Grafana (13.2.4) provisioned as code: Prometheus data source and a
  "Golden signals" dashboard (traffic, errors, latency p50/p95/p99, memory).
  The admin password is required from `.env`; the default admin/admin is off.
- `scripts/generate-traffic.sh` to feed the dashboards.
- Tests that check injected errors are counted (middleware order).
- CI: `promtool check config`, dashboard JSON validation and a smoke test
  that starts the whole stack and checks Prometheus and Grafana.

### Changed

- `/metrics` is excluded from chaos, so scraping keeps working while the app
  is failing on purpose.

## [0.1.0] - 2026-10-24

The victim app: a small service to break on purpose.

### Added

- `orders-api` (FastAPI + Postgres): `GET /products` and `POST /orders`.
- Liveness (`/healthz`, never touches the database) and readiness
  (`/readyz`, 503 when Postgres is down) probes.
- Programmable failures at `/admin/chaos`: error rate, latency on a fraction
  of requests and a memory leak. Off unless `FIREBREAK_CHAOS_ENABLED=true`.
- Docker image (`python:3.12.15-slim`, non-root user) and `compose.yaml`
  with Postgres 18, healthchecks and startup ordering.
- Tests with pytest that run without a database.
- Pre-commit hooks: gitleaks, ruff, yamllint, hadolint.
- CI on every pull request: lint, tests, compose validation, image scan with
  trivy and a full-history secret scan.
